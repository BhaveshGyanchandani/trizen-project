# Component Architecture — Trizen Photo Ops

This document describes the frontend's component layer: how the pieces
under `components/` and `app/` fit together, and which patterns are
deliberate conventions versus incidental leftovers. It complements
`architecutre_files/ARCHITECTURE.md` (system-level architecture) and
`docs/API_SPEC.md` (the backend contract these components call).

## Layers

```
components/ui/        shadcn/ui primitives (generated, style-only)
components/            App-level shared components (business-aware)
app/*/page.jsx          Route-level screens (compose the above)
app/*/layout.jsx        Route-group shells (auth gating, sidebar)
```

Screens under `app/` own data fetching and state; they compose
components from `components/` for presentation. Components in
`components/` are generally presentation-only and receive data/handlers
via props rather than fetching themselves — the one exception is
`AppSidebar.jsx` and `PhotoUploadForm.jsx`, which call `useAuth()` /
the photos API directly because their behavior is self-contained.

## `components/ui/` — shadcn/ui primitives

These are the standard building blocks generated by the shadcn/ui CLI
(Badge, Button, Card, Dialog, DropdownMenu, Input, Separator, Sheet,
Skeleton, Table, Tabs) plus a trimmed custom port of shadcn's Sidebar
pattern (`sidebar.jsx`) adapted for this app's simpler needs (no
icon-only collapse variant, no tooltip-on-collapse). They carry no
business logic — only style variants (via `class-variance-authority`)
and, where relevant, Radix UI's accessibility behavior (focus trapping,
keyboard navigation, portals).

Treat these as vendored code: re-run the shadcn CLI to update them
rather than hand-editing extensively, so upstream fixes aren't lost.

## `components/` — shared app components

### Compatibility wrappers

Several components are thin wrappers translating this app's older
prop vocabulary onto the newer shadcn primitives, so call sites across
~20 screens didn't all need updating in one pass when the design
system changed:

| Component | Wraps | Notes |
|---|---|---|
| `Badge.jsx` | `ui/badge.jsx` | Maps semantic tones (`neutral`, `published`, `draft`, `role`) to shadcn variants. |
| `Button.jsx` | `ui/button.jsx` | Maps legacy variants (`primary`, `secondary`, `secondary-paper`, `ghost`, `danger`) to shadcn variants. `secondary` and `secondary-paper` both collapse to `outline`. |
| `Modal.jsx` | `ui/dialog.jsx` | Same `open`/`onClose`/`title` prop shape as the old hand-rolled modal, now backed by Radix's Dialog for real focus-trapping and Escape-to-close. |
| `Field.jsx` | `ui/input.jsx` (via `inputClass`) | `inputClass()` returns the same classes as the shadcn `Input` for call sites that need to build a custom `<input>` (e.g. the PIN entry digits) rather than use `<Input>` directly. |

`EmptyState.jsx` and `Loader.jsx` accept a `tone` prop for historical
reasons but the current design uses one visual register throughout, so
`tone` no longer changes anything — it's kept only so existing call
sites don't need editing.

### Layout & navigation

- **`AppSidebar.jsx`** — the sidebar actually rendered by
  `app/admin/layout.jsx`, `app/team/layout.jsx`, and
  `app/profile/page.jsx`. Role-aware links, current-user identity, logout.
- **`Topbar.jsx`** — sticky page header used at the top of every
  admin/team screen (mobile sidebar trigger, eyebrow, title, actions slot).
- **`KpiRow.jsx`** / **`SummaryStrip.jsx`** — headline stat cards for
  dashboard homes (`KpiRow`) and a smaller inline variant for an
  event's detail page (`SummaryStrip`).

> **`Navbar.jsx` and `Sidebar.jsx` are not used anywhere in this
> codebase.** They appear to be an earlier top-nav / hand-rolled
> sidebar design, superseded by `AppSidebar.jsx`. They're left in place
> for reference (each carries a `NOTE:` comment saying so) but should
> be deleted once confirmed unnecessary, to avoid confusing future
> contributors about which sidebar is live.

### Domain components

- **`EventCard.jsx`** — one row in an events list: thumbnail, name,
  counts, status badge.
- **`PhotoGrid.jsx`** — the single shared grid used across the admin
  curation view, the team upload/review view, and the public gallery.
  Its behavior is entirely prop-driven (see the JSDoc on the component
  for the full prop matrix) rather than split into three near-duplicate
  grids, so photo-tile rendering, lazy image fallback, and layout stay
  in one place.
- **`PhotoUploadForm.jsx`** — drag-and-drop/file-picker upload widget
  used by team members. Owns its own upload queue and progress state.
- **`PinEntryForm.jsx`** — the 6-digit PIN form on the public gallery
  landing page.

## `app/` — route-level screens

Routes are grouped by audience:

- **`app/(auth)/`** — `login`, `register`. Public, centered single-column layout.
- **`app/admin/`** — admin-only screens, gated by `app/admin/layout.jsx`
  (redirects non-admins). Dashboard, per-event workspace (the largest
  screen in the app — team assignment, photo review, gallery publish
  lifecycle, customer request review), and team/account management.
- **`app/team/`** — team-member-only screens, gated by
  `app/team/layout.jsx`. Dashboard and per-event upload/review workspace.
- **`app/profile/`** — shared by both roles; does its own lightweight
  auth check rather than living under either role-gated layout, since
  the backend route it calls (`/api/auth/profile`) is already scoped
  to "whoever is authenticated."
- **`app/gallery/[slug]/`** — the public, unauthenticated customer
  gallery: PIN gate, then browsing, rating, and change-request UI.
- **`app/page.js`** — the public marketing landing page.

Each admin/team page generally follows the same shape: a `load()`
function that fetches its data on mount, local optimistic-update
handlers for user actions (with rollback on failure — see
`handleTogglePhoto` in the admin event page for the clearest example),
and one or more modal sub-components defined in the same file for
forms that only that screen uses.

## State & cross-cutting concerns

- **`lib/useAuth.js`** — app-wide session context (`AuthProvider`,
  `useAuth()`). Wraps the whole app in `app/layout.js`.
- **`lib/useToast.js`** — app-wide toast notifications (`ToastProvider`,
  `useToast()`). Also wraps the whole app in `app/layout.js`.
- **`lib/api.js`** — the only place `axios` is imported outside of
  itself; every screen calls into the grouped API objects here rather
  than making requests directly. See `docs/API_SPEC.md` for the
  request/response contract each function corresponds to.
- **`lib/idOf.js`** — normalizes `id` vs. `_id` across API responses.

## Known cleanup items

These are called out here (and with inline `NOTE:` comments at each
file) so they aren't mistaken for active code during a future edit:

1. **`components/Navbar.jsx`, `components/Sidebar.jsx`** — dead code,
   superseded by `AppSidebar.jsx`.
2. **`lib/jwtAuth.js`** — dead code, superseded by `lib/authHelper.js`.
   Also contains a hardcoded JWT secret fallback that `authHelper.js`
   deliberately avoids — do not reintroduce this pattern if reviving
   any code from this file.
3. **`src/`, `vite.config.js`, `index.html`** — leftover `create-vite`
   scaffolding, not part of the Next.js app that actually builds and
   runs (see `package.json` scripts).
4. **Duplicate PIN/slug generators** — `generatePin`/`generateSlug` are
   defined once in `lib/galleryPublish.js`, but
   `app/api/events/[id]/gallery/publish/route.js` and
   `.../regenerate-pin/route.js` each redefine a local copy instead of
   importing the shared one. Functionally harmless (the logic is
   identical) but worth consolidating.
